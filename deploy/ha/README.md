# Three-node HA deployment

Implementation candidate: the original single-host application remains live until the HA cluster, import and failover checks complete. Do not interpret provisioned nodes as a verified HA service. Record final evidence in docs/submission-status.md after migration.

Three Bangalore Ubuntu 24.04 Droplets each host an application replica, Kafka broker/controller, PostgreSQL/Patroni member and etcd voter. A DigitalOcean regional load balancer fronts three TLS proxies. Kafka uses RF=3, min ISR=2, acks=all, idempotent producers, distinct UUID keys and no unclean election. PostgreSQL uses Patroni strict synchronous mode, one synchronous standby, remote_apply commits, timeline checks and required watchdog fencing. If safe quorum/durable replication is unavailable, writes fail or block instead of acknowledging an unsafe commit. Do not force promotion of an asynchronous replica.

Control-plane, PostgreSQL and Kafka CAs are separate. Only peer VPC addresses can reach cluster ports. Kafka clients have mutual TLS plus topic/group ACLs; they cannot access control-plane credentials. Application PostgreSQL connections verify server identity and select the writable primary from all three addresses. Three workers share lease/fencing state in PostgreSQL. Public HTTPS certificates/challenges use shared PostgreSQL-backed Caddy storage and distributed locks; the third-party storage module is pinned and scanned with the custom proxy image. Database failure can temporarily prevent cold proxy startup/renewal; already-loaded certificates remain in memory.

CI builds and scans the HA database/backup and proxy images, tests a real three-member TLS PostgreSQL/etcd failover with acknowledged rows, and signs the runtime artifact. The CI fixture disables watchdog only because all test containers share a disposable runner host. Production rendering always requires the watchdog. Use install-runtime.sh as the existing root operator to verify/install that signed infrastructure artifact. Keep offline CA private keys off the Droplets. The application promotion gateway accepts only signed bundles; deploy-ha.yml drains and updates one backend at a time. HA_ENABLED and HA_DEPLOY_READY prevent the legacy single-host deployment from being triggered during migration.

## Backup and restore

Use one private Standard Spaces bucket, with public listing and CDN disabled. Its limited access key is scoped to that bucket only. Spaces holds age-encrypted archives; a separate secret authenticates completion manifests. The age private identity and manifest key must also be retained securely outside the Droplet cluster, separately from the bucket. Neither belongs in Git. Roles/passwords and server configuration must be recovered from protected deployment configuration, because pg_dump backs up database objects/data, not the PostgreSQL cluster's login roles.

notification-backup.timer runs a due-time and retention check every five minutes on all nodes. A PostgreSQL session advisory lock serializes jobs. The first successful job creates the daily snapshot; subsequent checks skip another successful backup that UTC day. A repeatable-read exported snapshot makes dump and recorded table counts consistent. An incomplete upload never gets a completion manifest. Encryption, SHA-256 and an authenticated manifest are checked before restore preparation.

The requested retention is **24 hours**, with up to five minutes plus timer jitter for healthy-cluster cleanup. Only the dedicated postgres/daily/v1 prefix and strict backup filenames are eligible for deletion. Old backups expire even if the next backup fails, as required by the one-day-only policy; this can leave no backup. A whole-cluster outage can delay the application-side pruning job. Check provider lifecycle availability separately; do not claim a lifecycle policy has been configured unless the API confirms it.

Run restore-test.sh MANIFEST_KEY on a node as the operator. It downloads from Spaces, authenticates the manifest, verifies the encrypted object, decrypts with age, checks the dump digest, restores a fresh network-isolated PostgreSQL 17 database, compares every recorded business/audit/schema-history table count, and removes the disposable target/plaintext files. It never overwrites the production database. Recovery of the actual service additionally requires provisioning roles, applying runtime grants, replacing the failed cluster and validating the application before opening ingress.

## Guarantees and limits

The target RPO is zero for **acknowledged event commits through a single-node failure**, with a surviving quorum and strict synchronous replication intact. Client requests with an uncertain response must reuse their idempotency key. Webhooks can repeat; receivers must deduplicate deliveryId. Finite retries do not guarantee eventual subscriber receipt.

This three-node same-region topology does not survive arbitrary simultaneous disk loss, operator corruption or a region-wide disaster with zero loss. A daily full backup has up to roughly 24 hours of recovery-point loss after total cluster destruction; it is not continuous WAL/PITR. One-day retention also cannot recover corruption discovered after that window. Region/host-loss guarantees must not be conflated with measured failover results. Renew 90-day internal certificates before expiry; preserve the offline signing keys and trusted roots.

Estimated base: 3 x $24 Droplets + $12 regional load balancer + $5 Standard Spaces = about $89/month, excluding taxes/overages. The cluster remains Bangalore; new Bangalore Spaces creation is disabled in this account, so the private backup bucket is Singapore. Source/versioned scripts are separate from root-only node inventory and secrets under /opt/notification-fanout/ha.
