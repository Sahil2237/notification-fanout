## Health and incident checks

Use `/health/live` for process health and `/health/ready` for Redis/database/worker/Kafka readiness. Inspect all three nodes, not only one successful load-balanced request. On a node, use root-owned `/opt/notification-fanout/ha/compose.yaml` and `node.env` with Compose project `notification-ha`. Internal ports require peer VPC access and appropriate TLS credentials. Public ingress rejects administrator paths; use an operator SSH tunnel for origin management. Do not print `secrets.json`, `backup.env`, DSNs, keys or event bodies in logs.

Metrics include acceptance latency, pending jobs/age, attempts/failures, Kafka publication/dispatch/quarantine errors and JVM/database pools. Logs carry request/event/delivery identifiers. Host monitoring is installed; external dashboards and paging are not configured. Suggested alerts: no ready backend, database without a synchronous standby, Kafka ISR below two, pending age over 60 seconds, growing quarantine, disk over 85%, backup failure or no successful backup in 26 hours, and internal certificates approaching expiry. These are operating targets, not an established production SLO.

For a 503, distinguish admission capacity, database failover/quorum and readiness. Never disable synchronous commits, force an asynchronous promotion or enable Kafka unclean election to recover availability. Check Patroni roles/lag, etcd quorum and the watchdog boot dependency first. Check all Kafka event partitions for ISR, then outbox age and consumers. Outbox redrive can republish an event after a crash; uniqueness prevents duplicate jobs. HTTP outcomes can remain uncertain; receivers must deduplicate deliveryId. Terminal failed deliveries require an explicitly authorized repair/replay plan; there is no replay endpoint.

## Application releases and rollback

GitHub CI verifies Java/Python tests, real service startup, failed-release rollback, database restoration, real synchronous PostgreSQL failover, proxy behavior and fixable HIGH/CRITICAL image scans. It signs the exact tested image artifacts. The restricted upload account has no Docker membership or secret access; the root promotion gateway verifies the trusted signature, paths, checksums, revision and portable image identity.

`deploy-ha.yml` promotes one application at a time. `ha-release.sh` drains the backend, runs forward migrations, starts the verified application, checks readiness, persists APP_IMAGE in node.env and the successful app-sha, then removes the drain. Failure halts further nodes and attempts to restore the previous app where available. Schema migrations are not reversed. Keep migrations additive and compatible with both versions during a rollout. A destructive migration requires a separate backed-up recovery plan. Daily Spaces backups are separate from application promotion; HA promotion does not promise an additional pre-migration snapshot.

Infrastructure updates are separate operator operations: verify signed runtime artifacts and image identity, update one member, wait for database streaming/synchronous replication, etcd quorum, Kafka ISR=3 and application readiness before touching another. Docker requires notification-watchdog.service before startup. Run `deploy/ha/test-watchdog-boot.sh` after every host reboot, including watchdog fencing. Use a safe Patroni switchover before planned primary maintenance. Do not upgrade all nodes concurrently.

The old single-host containers are stopped with their volumes retained. Their database became stale when HA accepted its first new write. It is not an automatic rollback database and must never be reopened as authoritative. Do not delete its volumes as routine cleanup.

## Daily Spaces backup and restore

All three nodes run notification-backup.timer every five minutes with jitter. A database advisory lock permits one successful snapshot per UTC day; another node can run it after a host failure. The job uses a consistent exported snapshot, disk-backed protected scratch, age encryption, SHA-256 and an authenticated completion manifest published last. A bucket-scoped key permits only the selected private bucket. The decryption identity is absent from two nodes and is also retained in the protected development workspace outside the cloud cluster.

As root, run `systemctl start notification-backup.service`, then inspect its journal for backed_up or not_due. The current tools image is pinned in `/opt/notification-fanout/ha/tools-image`. Do not fetch production dumps onto the workstation. Test a completed manifest with `bash /opt/notification-fanout/ha/restore-test.sh postgres/daily/v1/TIMESTAMP-UUID.json` on the host retaining the protected age identity. The script authenticates/decrypts actual Spaces objects, checks the dump hash, restores into a disposable network-isolated PostgreSQL 17 database, compares the table counts declared by the snapshot (current metadata covers thirteen tables; historical snapshots can cover nine), and removes disposable plaintext/containers. It does not overwrite production.

Retention is 24 hours plus up to five minutes and timer jitter while the cluster is healthy. Only strict backup filenames under postgres/daily/v1 are eligible for pruning. If a new backup fails after the old one expires, there may be no recoverable snapshot. A complete cluster outage delays cleanup. A provider lifecycle policy has not been installed: the scoped key cannot change bucket lifecycle settings. Retention boundary and namespace restrictions have automated tests; an elapsed 24-hour cloud expiration cycle has not yet been observed.

A daily backup has up to roughly 24 hours of data loss after total cluster destruction. It is not continuous WAL/PITR. Restoring the entire service also requires recovering roles, configuration, TLS and credentials, establishing a new synchronous cluster, granting application rights, rebuilding Kafka and republishing outbox work, then checking audit and synthetic delivery before traffic. Database snapshots do not contain PostgreSQL login roles or the Caddy certificate database. Secure long-term escrow of recovery identities, the manifest key and deployment credentials outside both cluster and bucket remains an operator handoff requirement; do not rely on the development VM as the only durable escrow. Never put these secrets in Git. A full-region disaster recovery time has not been measured.

## Other retention and security operations

Events, attempts and audits are not automatically deleted because business retention and idempotency expiry were not specified. Monitor storage growth. Backup retention does not delete application history. Origin approval/revocation is stored in PostgreSQL and read by every replica at registration and each attempt; there is no approval cache to invalidate. Already in-flight HTTP requests may finish after revocation.

Renew internal certificates before their 90-day expiry; offline signing authorities remain off the cloud hosts. Monitor automatic public certificate renewal separately. Rotate tenant/admin/signing, database, CI SSH, release-signing and Spaces credentials through coordinated procedures; changing a configuration file alone does not change database roles. Root operators and repository signing/write access remain trusted. No claim of exhaustive security testing, zone-placement independence, zero-loss regional disaster recovery or 10,000-events/second capacity follows from this assessment deployment.


## Shared Redis and current release controls

Redis/Sentinel run under separate Compose project `notification-rate`, configuration `/opt/notification-fanout/ha/redis/compose.yaml`, private TLS ports6379/26379. Never rerun bootstrap over persistent Sentinel/Redis configuration: elected-primary addresses/epochs must survive restart. The offline Redis CA private key is not on the Droplets. Application credentials can update only quota keys and discover a primary; they cannot force failover or flush the store. Do not print ACL files, secret-bearing command arguments or complete container environments during diagnosis.

For429 check the tenant window and Retry-After; for503 check Redis TLS/auth, current primary, connected replicas and acknowledgements before changing admission policy. Do not add a local or SQL fallback. A Redis failover can lose counters despite WAIT; it is not strict entitlement accounting. Shared tenant allowance is 6,000/minute; there is no separate per-user allowance. Retry budgets are separate tenant/subscription counters.

The first cross-contract cutover used root-owned coordinated-cutover/drain flags on all hosts and stopped old workers before migrations. It completed on 24 November 2026; flags are absent, all apps run 6474ad3 and HA_DEPLOY_READY is true. Compatible future releases use the normal rolling gateway; incompatible ownership/identity migrations need a separately planned coordinated cutover. Signature verification compares portable filesystem/execution identity because Docker engines can report different image ID forms. Never bypass verification based on a matching tag alone.

Backup-only tools now use the verified6474ad3 tools image without changing the running PostgreSQL/etcd/Kafka/proxy images. Current snapshot metadata includes delivery_dead_letters; the backup role's access to that table was checked. The actual Spaces restore in historical evidence validated a nine-table snapshot; a new ten-table Spaces restore was not executed in the controls rollout.

A container crash can be restarted by Docker unless-stopped on a surviving host; a whole lost Droplet is not automatically replaced. No horizontal autoscaler or autoheal controller is deployed. Two whole-host failures remove safe quorum/replication and normal admission must fail, while losing two app containers alone need not stop the remaining app if infrastructure is healthy.

For public ingress, SSH scope, broad outgoing rules, ETag/idempotency boundaries and the verified load-balancer health/affinity settings and provider-managed distribution contract, use [the network/security contract](network-security.md). Alarms and incident tickets are intentionally not deployed; the earlier suggested signals are future operational guidance, not active alarm configuration.
